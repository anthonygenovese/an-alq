# Threat model

Scope is the code in this repository and one designed component that is not implemented. The product is educational. Quantitative figures are illustrative. There is no real RF, jamming, spoofing, or geolocation. The T2 exercise picks a cell on a fictional grid. It is not a fix.

Reviewed: November 2026, against the MCP server v0.1 and the T1 range trainer.

## Assets

| Asset                    | Why it matters                                                                                                  |
| ------------------------ | --------------------------------------------------------------------------------------------------------------- |
| Catalog integrity        | Callers treat tool output as the project's public statement. A tampered file would put words in that statement. |
| The no-echo rule         | Error strings and logs must not repeat a ZIP, an address, a header, or a body.                                  |
| Rate-limit fairness      | One caller should not pin the process. The bucket must not be forgeable.                                        |
| On-device skill evidence | Aggregate counts in the browser. Low sensitivity, still not for a server.                                       |
| Future relay credential  | Not in the repo. Called out so it is not invented casually.                                                     |

## Actors

| Actor               | Can                                                                             |
| ------------------- | ------------------------------------------------------------------------------- |
| MCP client          | Send JSON-RPC to `/mcp` or over stdio.                                          |
| Browser player      | Run the trainer locally. Read and write their own `localStorage`.               |
| Hostile HTTP client | Send a large body, a forged forwarded-for header, a hostile `Host` or `Origin`. |
| Maintainer          | Merge to `main`, cut a release, hold the only production credentials.           |
| Future relay        | Not built. Would hold a posting credential and read public alerts.              |

## Assumptions

- The Vercel function is reached through Vercel, which sets `x-vercel-forwarded-for` and strips a client-supplied copy of that header.
- The local server binds to loopback unless `HOST` is changed on purpose.
- The content files in git are the content files the process reads. There is no admin upload.
- The trainer bundle does not embed a secret. `pnpm --filter @an-alq/sim build` only compiles the catalog and the UI.

## STRIDE — Nixle signal relay

The relay reads public alert text. It does not post to X, send mail, or hold a Gmail token. Code lives in `apps/relay`. A receipt vote is separate from a relay pulse.

A verified receipt looks at the five newest **Nixle** messages in the inbox, not the five newest messages of any kind. The browser calls `users.messages.list` with `labelIds=INBOX`, `q=from:(nixle.com OR nixle.us)`, and `maxResults=5`. Gmail applies that sender filter. Promotions, mailing lists, and other mail are not returned and are not fetched. The sender list is the same domains that publish Nixle DKIM keys (`nixle.com`, and `nixle.us` if a message uses it). If that query is rejected, the client may walk inbox ids and read only the `From` line, discarding it immediately, and still count only Nixle senders toward the five. It does not fetch a non-Nixle body.

`gmail.readonly` still permits a full mailbox read. The five-Nixle cap is self-enforced by this client. It is not a restriction Google applies to the scope. The server cannot prove the message was inside those five. What the server can enforce is the DKIM-signed `Date` header: it must fall within the freshness window (default 60 minutes) of submission. In the non-ZK fallback, the server instead requires the alert's own first-seen time to sit inside that window. An old alert read later does not vote.

| Threat                 | What the code does                                                                                                                                                                     |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Spoofing               | A vote needs a ZK receipt (verifier interface; the circuit is not linked yet) or a fallback against an alert the process already holds. The scaffold verifier does not accept a proof. |
| Tampering              | Ingest and vote bodies are strict. Address headers, tokens, and message ids are rejected.                                                                                              |
| Repudiation            | A nullifier stops a second vote on the same signal. It is not a person id, and it is deleted when the signal decays.                                                                   |
| Information disclosure | No sender, recipient, mailbox address, or Gmail token is stored. The token stays in the tab and is revoked on close, expiry, or disarm.                                                |
| Denial of service      | Fallback votes are rate limited. The inbox read is five Nixle ids.                                                                                                                     |
| Elevation              | Gmail scope is `gmail.readonly`. There is no send, modify, label, or delete call. X is a public read.                                                                                  |

Decay is the retention policy. A signal, its relay times, and its vote nullifiers stay in memory until the activity score falls or the inactivity TTL hits. Nothing is written to disk. There is no archive of who received an alert.

## Privacy summary

| Store                  | What is kept                                                                                                   | How it ends                                                                  |
| ---------------------- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| MCP process memory     | Hashed rate-limit keys and timestamps                                                                          | Window expiry, key cap, process exit, Vercel cold start                      |
| MCP disk               | Nothing                                                                                                        | —                                                                            |
| MCP logs               | Allowlisted fields, stderr                                                                                     | The platform's log retention, which should be short. No body is in the line. |
| Browser `localStorage` | Aggregate trainer counts, the barrage acknowledgment, and the fictional-grid acknowledgment and attempt counts | The player clears site data. The server never receives the records.          |
| Git                    | Sample content, fictional catalog, source                                                                      | Review. No secrets. gitleaks runs on the full history in CI.                 |

Anonymity is the absence of an identifier, not a hash of one that we then store. The address hash exists only inside the rate-limit map and is gone with the window.
